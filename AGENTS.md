# Project coding conventions

Apply the maintainability, naming, documentation, and testing guidance in [Coding best practices](https://en.wikipedia.org/wiki/Coding_best_practices) and [DataCamp's coding practices guide](https://www.datacamp.com/fr/tutorial/coding-best-practices-and-guidelines), using the concrete rules below for this project.

- Keep production code and catalog generation based on ChoCo.
- Comment every new or changed function, method, React component and hook with at least one line saying what it does: a docstring in Python, a `/** ... */` or `//` line in TypeScript. Explain any non-obvious behavior.
- Write comments in plain ASCII (no accents or typographic signs). In Python source, write non-ASCII text as `\u` escapes; user-facing text in the app may use typeset signs.
- Use descriptive names, small focused functions, and one implementation of each shared rule. Avoid duplicate conversion, matching, and catalog-writing logic.
- Before writing a helper, look for an existing one. Shared app code lives in: `studio/src/music/chords.ts` (keys, note names, transposition), `studio/src/audio/usePlayer.ts` (player setup and playback clock), `studio/src/audio/useMixer.ts` (part and master volumes), `studio/src/library/storage.ts` (browser storage), `studio/src/library/catalog.ts` (songs from the server or the bundled catalog: never fetch `/api/*` elsewhere), `studio/src/audio/nativeMidi.ts` (MIDI in the native app), `studio/src/ui/AppLink.tsx` (links between screens, top-bar title). Shared Python rules live in `chord_notation.py` (every chord, key and Roman spelling; see docs/CHORD_NOTATION.md), `track_store.py` (writing catalog tracks), `song_dedupe.py` (duplicate and similar songs), `score_search.py` (song identity, source priority), `studio_bridge.py` (charts, keys), `find_progressions.py` (progression matching) and `key_modes.py` (settling uncertain key modes).
- Players and exercises that play the band: a setting that does not change the sheet being played (style, piano pattern, choruses, guide melody, any octave, timing, the band on or off, mixer...) must not stop or restart the song, nor play a new count-in: arrange again and go on from `player.position` (`player.play(midi, fromSeconds)`). Only a change of the sheet (another song, key, loop, lick...) starts again. Endless exercises hand over to their next chunk with `player.queue` and `player.startQueued`, so there is no gap or reset noise.
- Update the documentation (README.md, docs/, studio/README.md, PATTERN_AUDIT.md) in the same change as the code or data it describes.
- Keep generated files reproducible from their source scripts. Rebuild `data/common_progressions.json` with `python find_progressions.py`; do not edit it by hand.
- Rebuild the database with `python build_database.py` (sources in `data/sources.json`), then the catalog and the exercise. New data comes in as a source adapter yielding `track_store.Track`; data corrections live in the correction zips and the adapters, never in hand-edited data. Store chords only through `chord_notation`.
- Rebuild `data/left_hand_patterns.json` with `python left_hand_patterns.py`; keep pattern rules in that one module.
- Rebuild `studio/public/exercises/name-progression.json` with `python build_exercises.py` after the progression catalog changes, and the mobile catalog (`studio/public/catalog/`) with `python build_mobile_catalog.py` after the database or the catalog changes; see docs/MOBILE.md.
- Add or update meaningful tests when changing conversion or matching behavior. Keep Python tests in `tests/` and run `python -m unittest discover` from the project root, and `pnpm test` in `studio/` for app changes, before reporting completion.
